<!-- sdlc:auto:start overview -->
Performance management System (PMS) is a two-app monorepo generated by the Quorq AI SDLC platform. backend/ is a FastAPI 0.115 service using SQLAlchemy 2.0, Pydantic 2, and Alembic migrations. It uses SQLite by default (DATABASE_URL overrides it), and docker-compose.yml provides PostgreSQL 16 and Redis 7. The API exposes cookie-based authentication with login, logout, password change, and invitation/reset token links. It also covers HR employee management (create, edit, manager assignment, deactivation, invitations, password resets), goals with manually entered progress, status, weighting, soft delete and audit history, a self-service profile with photo upload (resized with Pillow and stored through app/storage.py), and a /health probe. frontend/ is a Vite 6 + React 19 + TypeScript single-page app using React Router 7, TanStack Query, and Tailwind CSS 4. It has one module per approved screen under src/screens and calls the API through src/lib/api.ts. GitHub Actions builds and pushes the backend image to AWS ECR and deploys the frontend to AWS Amplify on every push to main. Note that the READMEs are partly stale: the root README says the backend has only a health check, and the frontend README says the screens run on seeded sample data. The routers and the src/lib API modules show substantially more than that.

<!-- sdlc:auto:start prerequisites -->
- Python 3.12 (the version in backend/Dockerfile) with pip
- Node.js and npm for the Vite 6 / React 19 frontend
- Docker with Docker Compose (optional): runs local PostgreSQL 16 and Redis 7 from docker-compose.yml and builds the backend image
- Chromium for Playwright, installed with `npm run test:e2e:install`

<!-- sdlc:auto:start setup -->
1. cd backend
2. python -m venv .venv   # Playwright's webServer runs the API from backend/.venv
3. source .venv/bin/activate
4. pip install -r requirements.txt
5. alembic upgrade head   # main.py says the schema is managed only by Alembic, never created at startup
6. uvicorn app.main:app --reload   # API on http://localhost:8000 (SQLite ./app.db unless DATABASE_URL is set)
7. # In a second terminal:
8. cd frontend
9. npm install
10. npm run dev   # the SPA calls VITE_API_BASE_URL, which defaults to http://localhost:8000
11. # Optional: use Postgres instead of SQLite. From the repo root run `docker compose up -d db`, then before running alembic and uvicorn: export DATABASE_URL=postgresql+psycopg://app:app@localhost:5432/app
12. # If the frontend runs on an origin other than the backend's default, set ALLOWED_ORIGINS (comma-separated) for the backend's CORS middleware
<!-- sdlc:auto:end setup -->

<!-- sdlc:auto:start conventions -->
- Backend: one APIRouter per architecture component, all included in app/main.py.
- Every request passes the app-wide `auth.require_custom_header` dependency. The frontend client sends `X-Requested-With: pms` on every non-GET request, and authenticates with a session cookie (`credentials: "include"`).
- Validation errors are returned as HTTP 422 with `{"errors": {field: "English message"}}`, one plain-English message per field. Password-rule failures also include `unmet_rules`.
- Access control uses roles `employee`, `manager`, `hr_admin`, and `executive`, enforced with `auth.require_role(...)` and `auth.current_employee`. Read access to an employee's record or goals is granted to that employee, HR admins, executives, and managers above them in the reporting chain.
- State-changing actions append an `AuditEvent` row and never update or delete existing audit rows. Goals are soft-deleted via `deleted_at`.
- Goal progress is always typed in by a person and never calculated. If no period is given, it is derived from the due date (`YYYY-Qn`).
- Schema changes go only through Alembic migrations (`alembic upgrade head`); there is no `create_all` at startup.
- Models use UUID primary keys, timezone-aware UTC timestamps, and lower-cased work emails.
- PATCH endpoints apply only the fields actually sent (`model_fields_set`).
- Frontend imports use the `@/` alias for `src/`.
- The frontend is TypeScript in strict mode, but with `noImplicitAny` and `strictNullChecks` turned off.
- Tailwind CSS 4 is styled through brand CSS variables such as `var(--brand-fg)`, defined in index.css and lib/brand.ts.
- Vitest component tests sit beside the components they cover (`*.test.tsx`), while Playwright specs live in `e2e/`.
- The UI is English-only: `document.documentElement.lang` is always set to `en`.
- Tooling: Ruff for Python linting and formatting; ESLint with typescript-eslint and Prettier for the frontend.

<!-- sdlc:auto:start troubleshooting -->
| Problem | Solution |
|---|---|
| Playwright cannot start the API (`.venv/bin/python` not found). | Create backend/.venv and install requirements into it (`cd backend && python -m venv .venv && .venv/bin/pip install -r requirements.txt`). The Playwright webServer command uses that path. |
| API calls fail with missing tables after a fresh clone. | Run `alembic upgrade head` in backend/. The app never creates the schema at startup. |
| The browser blocks API calls with a CORS error. | Set ALLOWED_ORIGINS (comma-separated) on the backend to include the frontend's origin. |
| POST, PATCH, PUT or DELETE requests from curl or other tools are refused. | Send the session cookie together with the header `X-Requested-With: pms`, which the app-wide `require_custom_header` dependency expects. |
| The deployed frontend calls localhost. | VITE_API_BASE_URL is inlined at build time. Set it before running `npm run build`. |
| `npm run build` passes but `npm run typecheck` fails. | This is expected: the build does not typecheck. Fix the reported types, often untyped `useState({})` usage, before relying on tsc. |
| Vitest picks up Playwright specs. | vite.config.ts limits Vitest to `src/**/*.{test,spec}.{ts,tsx}`. Keep Playwright specs in e2e/. |
| Using Postgres instead of SQLite. | Run `docker compose up -d db` and set DATABASE_URL to a psycopg URL such as postgresql+psycopg://app:app@localhost:5432/app, then run the migrations. |
| deploy.yml hard-codes values named *_API_SECRET_KEY in the frontend build environment. | Anything passed as VITE_* or NEXT_PUBLIC_* is inlined into the public bundle, so treat these values as non-secret. Rotate them and move any real secret to GitHub secrets or a server-side setting. |
